Vy UI components are accessible out of the box. You use `<Checkbox>` or `<VyCheckbox>` and the right native accessibility data is already on the element — you don't wire anything up. This page explains how that works, because it differs from the web.

## Why the web mental model doesn't transfer

On the web, the **element** carries accessibility. You write `<button>` and the browser gives you the button role, focusability, and state announcement for free; `<input type="checkbox">` announces checked/unchecked automatically. You only reach for ARIA when you build non-semantic widgets out of `<div>`s.

Lynx has **no semantic elements**. The vocabulary is essentially `<view>` (a generic box, like `<div>`), `<text>`, `<image>`, and `<scroll-view>`. A `<view>` has no inherent role or state. So *every* interactive control must be annotated — exactly like having to `role="button"` a `<div>` on the web — and the semantics can't come from the platform. They have to be supplied by the component.

::callout{icon="i-lucide-info" color="warning"}
Lynx ignores web `aria-*` attributes. Native accessibility is expressed through `accessibility-*` props (`accessibility-traits`, `accessibility-value`, `accessibility-label`, …), verified against `@lynx-js/types`.
::

## `useA11y` — the one place semantics are mapped

Every Vy UI primitive describes its own semantics with the `useA11y` composable and spreads the result onto its root element. The composable owns the mapping from a friendly descriptor to the correct native props:

```vue [CheckboxRoot.vue (inside @vyui/core)]
<script setup>
import { useA11y } from '@vyui/core'

// state comes from the component's own reactive logic
const a11y = useA11y(() => ({
  role: 'checkbox',
  state: isChecked.value ? 'checked' : 'unchecked', // → accessibility-value
  disabled: disabled.value,
}))
</script>

<template>
  <Primitive v-bind="a11y" />
</template>
```

That descriptor produces, on the rendered `<view>`:

```html
<view
  accessibility-traits="button"
  accessibility-role-description="checkbox"
  accessibility-value="checked"
  accessibility-element="true"
/>
```

It's **reactive** — when `isChecked` flips, `accessibility-value` updates live, so VoiceOver / TalkBack announce the new state. And because the mapping lives in one composable, fixing or extending it (e.g. adding a web ARIA layer later) happens in a single place rather than across every component.

## You don't call `useA11y` to *use* a component

`useA11y` is how the **library** stamps semantics onto a primitive. As a consumer you never touch it — the accessibility is baked into the component. The only thing the component can't know is the human-readable label, so that's the one piece you pass:

::code-group
```vue [@vyui/core]
<script setup>
import { CheckboxRoot, CheckboxIndicator } from '@vyui/core'
import { ref } from 'vue'

const checked = ref(false)
</script>

<template>
  <!-- role, checked-state and focusability are already wired by the primitive.
       You only supply the label and your own styling. -->
  <CheckboxRoot v-model="checked" accessibility-label="Subscribe to newsletter">
    <CheckboxIndicator>✓</CheckboxIndicator>
  </CheckboxRoot>
</template>
```

```vue [@vyui/kit]
<script setup>
import { VyCheckbox } from '@vyui/kit'
import { ref } from 'vue'

const checked = ref(false)
</script>

<template>
  <!-- VyCheckbox is built on CheckboxRoot, so it inherits the exact same
       native a11y. You get styling on top and still just pass a label. -->
  <VyCheckbox v-model="checked" accessibility-label="Subscribe to newsletter" />
</template>
```
::

Both render the same `accessibility-*` output. `@vyui/kit`'s `VyCheckbox` wraps the core `CheckboxRoot`, so the accessibility comes through unchanged — kit only adds the Tailwind Variants styling.

## The descriptor

| Field | Maps to | Example |
| --- | --- | --- |
| `role` | `accessibility-traits` (+ `accessibility-role-description`) | `'button'`, `'checkbox'`, `'switch'`, `'tab'`, `'slider'`, `'dialog'` |
| `state` | `accessibility-value` | `'checked'`, `'expanded'`, `'selected'`, `'on'`, `'pressed'` |
| `value` | `accessibility-value` | `{ now: 30, max: 100 }` → `"30 of 100"` |
| `label` | `accessibility-label` | `'Subscribe to newsletter'` |
| `disabled` | flips the trait to `'disabled'` | `true` |
| `exclusiveFocus` | `accessibility-exclusive-focus` | modal/dialog focus trap |

::callout{icon="i-lucide-triangle-alert" color="warning"}
Lynx allows only **one** trait per element, so a disabled control announces `disabled` rather than `button` — the single-trait limit means it can't be both.
::

## Static vs stateful

- **Stateful controls** (checkbox, slider, accordion, dialog trigger) always go through `useA11y`, because the announced value has to recompute and stay in sync.
- **Static, stateless nodes** (a heading, a decorative separator) can just set a literal `accessibility-traits="header"` inline — no composable needed.

## Web later, as a no-op

Lynx does no bridging between native `accessibility-*` and web `aria-*`. `useA11y` keeps a single, currently-empty `appendWebA11y` step so a web ARIA layer can be added in one place later — emitting `role`/`aria-*` for the Lynx Web target while staying a no-op on native. Nothing in components needs to change when that lands.

## Status

Native semantics — roles, state announcements, valid traits, focusable nodes, and modal focus boundaries — are implemented across all interactive components and covered by per-component `*.a11y.test.ts` files. Still in progress: live-region announcements (`lynx.accessibilityAnnounce`) for transient UI like toasts, focus-movement into/out of dialogs, and the web ARIA layer. Track it in [issue #13](https://github.com/KealanAU/vyui/issues/13).
