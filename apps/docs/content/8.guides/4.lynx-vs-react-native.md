React Native has been the default answer to cross-platform mobile for a decade, and [Lynx](https://lynxjs.org/) is the first thing in a while that changes the shape of the question rather than the answer to it. ByteDance open-sourced it in March 2025 after using it in production across TikTok Studio and TikTok Shop, and the parts that differ from React Native are architectural rather than cosmetic.

Both frameworks render real native views, both let you write in a familiar frontend paradigm, and both ship to iOS and Android from one codebase, so the differences worth arguing about sit underneath all of that.

## Threading

React Native's New Architecture removed the asynchronous bridge that defined its first decade. JSI lets JavaScript hold direct references to native objects, Fabric renders synchronously, and bridgeless mode has been the default since 0.76. The result is that JavaScript and the UI thread coordinate closely, which fixed a long list of latency problems.

Lynx starts from a different assumption. It runs two threads by design, where the main thread does nothing but render and handle high-priority input, and your application code runs on a background thread beside it. Because the main thread never waits on user code to draw the first frame, a Lynx screen can paint before your components have finished evaluating, which is the property ByteDance built the framework around.

That split has a cost you feel when writing gesture code. A drag that tracks a finger at 60fps cannot round-trip to the background thread, so it runs in a main-thread worklet, a function marked to execute in the render realm with restricted access to the rest of your application state. React Native solves the same problem through Reanimated worklets, so the concept transfers, but in Lynx the two-realm model is the baseline rather than a library you add for animation.

## Styling

React Native styles are JavaScript objects implementing a subset of CSS through Yoga's flexbox. There is no cascade, no selector matching, and no stylesheet file, and the community has spent years building tools that approximate CSS on top of that foundation.

Lynx parses actual CSS from actual stylesheets. Selectors, custom properties, media queries, keyframe animations, and transitions all work, which means Tailwind and the rest of the CSS toolchain apply without an adapter layer. The limits that exist are specific rather than structural, and the one that bites first is that the native engine resolves only a single level of `var()` indirection, so a token that points at another token collapses.

For a team coming from the web, this is the difference that shows up fastest. Styling in Lynx feels like styling a website; styling in React Native feels like configuring a layout engine.

## Framework support

React Native is React, which for most teams is the reason to choose it rather than a criticism, though it does mean the framework decision and the platform decision collapse into one.

Lynx is deliberately framework-agnostic, with the rendering layer separated from the frontend that drives it. ReactLynx is the reference implementation and the most complete path, while [Vue Lynx](/guides/vue-lynx) provides a Vue 3 custom renderer that reuses `@vue/runtime-core`, and bindings for other frameworks are in progress. The Lynx team has said non-React frameworks already account for roughly half of the framework's usage internally.

For a Vue team this is the whole argument, because React Native offers no path that does not begin with learning React.

## Web

React Native targets iOS and Android, and web support comes from `react-native-web`, a community project that maps React Native primitives onto DOM elements. It works, and it is a translation layer rather than a first-class target.

Lynx treats web as a supported target with its own runtime, so the same source renders natively on mobile and through browser APIs on the web. Parity is not complete: Lynx dispatches raw mouse events without synthesizing touch, keyboard handling is thin because the framework was designed for touch first, and the `accessibility-*` properties that iOS VoiceOver and Android TalkBack consume are ignored by browsers. Component libraries have to close those gaps themselves, which [Vy UI does for pointer input](/getting-started/roadmap) across every gesture surface.

## Ecosystem

React Native wins the ecosystem comparison by a margin that no architectural argument closes. It has ten years of libraries behind it, Expo's entire toolchain, native module bindings for effectively anything you need, a hiring pool that already knows it, and a body of production experience covering every failure mode worth hitting. If your project needs a mature ecosystem more than it needs an architectural advantage, the comparison ends here.

Lynx is roughly a year into public life. The core is production-proven inside ByteDance at a scale most applications will never reach, but the surrounding ecosystem is early, third-party native modules are scarce, and component libraries number in the low single digits: the official headless [`@lynx-js/lynx-ui`](https://github.com/lynx-family/lynx-ui) for ReactLynx, and [Vy UI](/getting-started) for Vue Lynx. The [libraries comparison](/guides/lynx-ui-frameworks) covers what each of those contains.

## Choosing

Take React Native if you are shipping soon, need third-party native modules, are hiring against an existing talent pool, or already have React Native in production. The ecosystem advantage is real and it compounds.

Take Lynx if instant first-frame rendering matters to your product, if you want CSS rather than style objects, if the web target is a genuine requirement rather than an afterthought, or if your team writes Vue and rewriting into React is not a trade you want to make. Accept that you will occasionally be the first person to hit a given problem.

::callout{icon="i-lucide-flask-conical" color="warning"}
Lynx is stable, but Vue Lynx and Vy UI are both pre-1.0 and will introduce breaking changes. Choosing Lynx with ReactLynx is a considerably safer bet today than choosing it with Vue.
::
