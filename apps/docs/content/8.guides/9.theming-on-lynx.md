The [Theming section](/theming) documents the API: per-component theme files, Tailwind Variants overrides, runtime config, semantic colors, dark mode. This page is about the layer underneath, because Lynx renders through its own CSS engine rather than a browser, and several things that work in the web preview quietly do nothing on a device.

Each constraint below explains a design decision in Vy UI that otherwise looks arbitrary, and each will bite you the same way if you write your own theme without knowing about it.

## Lynx resolves one level of `var()`

This is the one that costs the most time, because it fails only on device. A browser resolves custom properties recursively, so a token pointing at another token pointing at a value works fine. Lynx's native engine resolves a single level, and a chain longer than that evaluates to nothing.

The failure is visual rather than diagnostic. Backgrounds come out white, borders come out black, and the console says nothing.

That is why Vy UI's semantic tokens hold concrete values rather than references to other tokens:

```css
/* packages/kit/src/style.css — concrete, not var(--ui-color-slate-500) */
--ui-text-muted: theme('colors.slate.500');
--ui-bg-muted:   theme('colors.slate.50');
```

Writing `--ui-text-muted: var(--ui-color-neutral-500)` would read more nicely and would work perfectly in the browser preview, then collapse on a phone. Dark mode flips the same tokens to their own concrete values rather than repointing them at a different chain.

The exception worth knowing is that `var()` does resolve inside `linear-gradient()`, which is device-proven, so gradient stops can stay as tokens and flip with `.dark` for free.

**Rule for your own themes:** a custom property may hold a value. It may not hold another custom property.

## Most Tailwind utilities do not exist

`@lynx-js/tailwind-preset` allowlists 57 of Tailwind's 179 core plugins and disables the rest, since a class emitting CSS the engine cannot parse is a silent no-op rather than an error. The [Tailwind on Lynx guide](/guides/tailwind-on-lynx) covers the mechanism and the v3 version pin that comes with it.

The practical consequence for theming is that the `ring` family is gone entirely, so a focus ring cannot be `ring-2 ring-primary-200`. What works instead is a spread-only `box-shadow`, which the engine does handle, with a single-level `var()` inside it:

```
shadow-[0_0_0_2px_var(--ui-color-primary-200)]
```

Focus itself is tracked in JavaScript rather than through `:focus-visible`, because the selector is not part of the supported set either.

## `data-[state]` selectors do not match

Component libraries on the web lean on `data-state="open"` with `data-[state=open]:` variants to style state. Lynx does not match attribute selectors that way, so those variants compile to CSS that never applies.

Vy UI keeps the `data-state` attributes, because assistive technology and consumers read them, and drives the styling from parallel `ui-*` classes generated by the Lynx preset's `uiVariants` plugin. Registering the kit's extra states is a step in [installation](/getting-started/installation) that is easy to skip:

```ts [tailwind.config.ts]
import { createVyuiPreset, VYUI_UI_STATES } from '@vyui/kit/tailwind'

const lynxPreset = createLynxPreset({
  lynxUIPlugins: {
    uiVariants: {
      prefixes: defaults => ({ ...defaults, ui: [...defaults.ui, ...VYUI_UI_STATES] }),
    },
  },
})
```

`VYUI_UI_STATES` covers `on`, `off`, `completed`, `highlighted`, `inactive`, and `dragging`. Skipping this leaves components rendering in their default state forever, with no error to tell you why.

## Icons ignore text color

Lynx rasterizes SVG rather than rendering it live, so an icon does not inherit `color` from its parent and `text-primary-500` on a wrapper does nothing. The color has to be baked into the icon at render time, which is what `resolveColorHex` exists for:

```ts
import { resolveColorHex } from '@vyui/kit'
```

Size works the same way, through the component's `size` prop rather than `w-*` and `h-*` utilities.

One more thing about icons: Lynx's `<svg>` support does not include masks, so mask-based icon sets render as solid boxes. Picking a non-masked variant is the whole fix, but it looks like a styling bug until you know.

## Dynamically built classes need a safelist

A class assembled at runtime, such as `` `bg-${color}-500` ``, cannot be extracted by Tailwind's scanner, which only sees literal strings in your source. On the web a missing utility usually degrades to something visible. On Lynx it degrades to nothing, so a component simply renders untinted.

Any color slot you construct dynamically needs to appear literally somewhere Tailwind scans, or be listed in `safelist`. Colors without a shade suffix, like `text-primary` or `bg-success`, need the same treatment.

## What this adds up to

Four rules cover almost all of it. Keep custom properties one level deep. Assume a utility does not exist until you have seen it render on a device. Style state through `ui-*` classes while keeping `data-state` for accessibility. Give icons an explicit color and size rather than expecting inheritance.

The browser preview is still the right place to do most theming work, since it is far quicker and the majority of what you write behaves identically. Just treat a device check as mandatory before calling a theme finished, because every failure mode above is invisible in a browser.
