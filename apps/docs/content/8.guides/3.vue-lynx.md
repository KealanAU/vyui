Vue Lynx is a Vue 3 custom renderer that targets [Lynx](https://lynxjs.org/), the cross-platform framework ByteDance open-sourced in March 2025 and uses in parts of TikTok. Your components stay Vue, written with `<script setup>`, the Composition API, and ordinary reactivity, but they render to native views on iOS and Android instead of to the DOM. The same source also runs on the web through Lynx's browser runtime.

Vue Lynx reuses `@vue/runtime-core` directly rather than reimplementing Vue, which is the detail that decides how much of your existing knowledge carries over. Reactivity, lifecycle, `provide`/`inject`, slots, and the component model behave the way they do in any Vue application, because they are the same code running underneath a different renderer.

## What changes

Four differences show up in the first hour, and none of them touch the component model.

**The elements are Lynx elements.** There is no `<div>` or `<span>`. Layout goes in `<view>`, text goes in `<text>`, and text must be inside a `<text>` element rather than loose in a container. Images use `<image>`, scrolling uses `<scroll-view>`, and long lists use `<list>`, which is a native recycler rather than a rendered array.

**Your code runs on a background thread.** Lynx splits work across two threads, where the main thread does nothing but render and handle high-priority input, and your JavaScript runs alongside it in the background. That separation is why a Lynx app can paint its first frame before your component code has finished executing, and it is also why a gesture that needs to track a finger at 60fps has to run in a main-thread worklet rather than in a normal event handler. Most components never touch this, but drag-driven ones do.

**Browser globals are gone.** There is no `window` and no `document`, so any library that reaches for them needs adapting or replacing. This rules out most of the existing Vue component ecosystem, which is the practical reason a Lynx-specific component library has to exist at all.

**Styling is real CSS, with limits.** Lynx parses actual stylesheets rather than style objects, so selectors, custom properties, media queries, and transitions all work. The limits are specific rather than general: the native engine resolves only one level of `var()` indirection, and a handful of properties behave differently from the browser. You mostly write CSS the way you already do.

## Vue Lynx and ReactLynx

ReactLynx came first and remains the reference frontend for Lynx, so the documentation, examples, and the official [`@lynx-js/lynx-ui`](https://github.com/lynx-family/lynx-ui) component library all assume React. Lynx itself is framework-agnostic by design, and the Lynx team has said that non-React frameworks already account for roughly half of its usage internally, so Vue Lynx is not fighting the architecture.

What Vue Lynx is fighting is ecosystem age. It is earlier than ReactLynx, its API surface is still moving, and libraries written for ReactLynx cannot be consumed from Vue because they are React components. If you need the most-supported path today, ReactLynx is it. If your team writes Vue and a rewrite is not on the table, Vue Lynx is the path, and the gap you will hit first is components.

::callout{icon="i-lucide-flask-conical" color="warning"}
Vue Lynx is pre-alpha and Vy UI is alpha. Both will introduce breaking changes. Neither is ready for production.
::

## Where components come from

Lynx gives you five elements, so dialogs, sheets, selects, toasts, sliders, and every gesture surface are application code unless a library provides them.

[Vy UI](/getting-started) is that library for Vue Lynx, in two layers. [`@vyui/core`](/packages/core) ships 47 headless primitives that handle state, focus, keyboard, and gesture physics while leaving styling to you. [`@vyui/kit`](/packages/kit) ships 48 styled components on top of those primitives, themed through Tailwind Variants, for when you want to start from something that already looks finished. You can mix the two freely and drop from kit to core wherever the styled version stops fitting.

The [Lynx UI frameworks comparison](/guides/lynx-ui-frameworks) covers how this maps against the ReactLynx options if you have not settled on a framework yet.

## Starting a project

Install the Vy UI packages into an existing Vue Lynx application:

```bash
npm i @vyui/core @vyui/kit
```

A styled component then works the way any Vue component does:

```vue
<script setup>
import { VyButton } from '@vyui/kit'
</script>

<template>
  <view>
    <VyButton>Continue</VyButton>
  </view>
</template>
```

Two pieces of setup are specific to Lynx rather than to Vue, and both are covered in [Installation](/getting-started/installation): the bundler needs `includeWorkletPackages` configured so main-thread gesture code is registered, and Tailwind needs the Vy UI preset for the semantic token layer that drives theming and dark mode.

## What to expect on each target

Native iOS and Android are the targets Lynx was designed for, and behavior there is the most complete. Accessibility works through the platform screen readers without extra wiring, gestures run on the main thread, and animations are native.

Web is a real target rather than a preview, and the component previews throughout these docs are the web runtime running actual component code. It is not at parity with native, though. Lynx dispatches raw mouse events without synthesizing touch from them, so drag surfaces need explicit mouse handling, which Vy UI [ships for every gesture component](/getting-started/roadmap). Keyboard navigation is not wired, and `accessibility-*` properties that native screen readers consume are ignored by browsers.

Checking the components you actually depend on against the targets you actually ship to is worth doing early, because the gaps are specific rather than uniform.
