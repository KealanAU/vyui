Running `rspeedy dev` gives you three URLs, a QR code, and four keyboard shortcuts, and most people use one of those and ignore the rest. The parts that get skipped are the ones that make the device loop quick, so they are worth ten minutes.

```
Rspeedy v0.14.5 (Rsbuild v1.7.5, Rspack v1.7.12)

  ➜  Web        http://192.168.1.24:3000/main.web.bundle
  ➜  ∟ Preview  http://192.168.1.24:3000/__web_preview?casename=main.web.bundle
  ➜  Lynx       http://192.168.1.24:3000/main.lynx.bundle

●  Scan with Lynx

◆  http://192.168.1.24:3000/main.lynx.bundle?fullscreen=true

◆  Usage
│   r  Switch entries
│   a  Switch schema
│   h  Help
│   q  Quit
```

## The three URLs

**Web** is the raw web bundle. Opening it directly gives you the compiled output rather than a running app, so it is mainly useful for confirming a build produced something.

**Preview** is the shell you actually want in a browser. The `__web_preview` route wraps the web bundle in a page that boots the Lynx web runtime around it, and `casename` names which bundle to load. This is the fastest loop for layout and styling work, and it is also the least faithful, because gestures arrive as mouse events and `accessibility-*` properties do nothing.

**Lynx** is the native bundle, and it is what a device loads. Both a QR-code scan and a [custom host app](/guides/testing-with-xcode) fetch this URL.

The `web` and `lynx` bundles only exist if you declare both environments:

```ts [lynx.config.ts]
export default defineConfig({
  environments: {
    web: {},
    lynx: {},
  },
})
```

Dropping `web` removes the preview shell, and dropping `lynx` leaves the QR code pointing at a bundle that was never emitted.

## Why the QR URL has `?fullscreen=true`

[Lynx Go](/guides/testing-on-device) renders your app inside its own chrome by default, with a navigation bar above your content. That bar changes the available height and hides the top safe area, so anything you are trying to check about status-bar overlap or `env(safe-area-inset-top)` gives you the wrong answer.

Appending `fullscreen=true` drops the chrome and hands your app the whole screen, which is what it gets in a real build. The `schema` option is where that gets added:

```ts [lynx.config.ts]
pluginQRCode({
  schema(url) {
    return `${url}?fullscreen=true`
  },
})
```

Returning a plain string replaces the QR code's URL outright. Without the plugin's `schema` option the default is `(url) => ({ http: url })`, which is the bare bundle URL and the chrome-wrapped rendering.

## Cycling schemas with `a`

Returning an object instead of a string is the part worth knowing, because `schema` accepts `Record<string, string>` and the `a` key cycles through whatever you put in it. One `rspeedy dev` session then serves several ways of opening the same bundle without a restart.

```ts [lynx.config.ts]
import { pluginQRCode } from '@lynx-js/qrcode-rsbuild-plugin'

pluginQRCode({
  schema(url) {
    return {
      fullscreen: `${url}?fullscreen=true`,
      chrome: url,
      host: `vyhost://lynx?url=${encodeURIComponent(url)}`,
    }
  },
})
```

Pressing `a` rotates the QR code between those three, and the label prints above it so you know which one is on screen. The pattern earns its keep once you have more than one way to open the app: fullscreen for real layout checks, chrome for when you want Lynx Go's reload button, and a custom URL scheme for your own host build.

A custom scheme entry is how you get a host app onto the same QR workflow. Register the scheme under `CFBundleURLTypes` in the host's `Info.plist`, read the `url` query parameter on launch, and load it as the bundle URL. Scanning then opens your host rather than Lynx Go, which is otherwise a manual copy-paste every time your LAN address changes.

## Cycling entries with `r`

Multiple entries in `source.entry` become multiple bundles, and `r` cycles the QR code between them:

```ts [lynx.config.ts]
export default defineConfig({
  source: {
    entry: {
      main: './src/index.ts',
      onboarding: './src/onboarding.ts',
    },
  },
})
```

Both build on every save, and pressing `r` re-renders the code for the other one. Splitting a heavy flow into its own entry is a reasonable way to iterate on it without booting through the rest of the app, though it does mean two bundles rebuild on every keystroke.

`h` reprints the usage block, and `q` shuts the server down.

## Picking a surface

Roughly, the more faithful the surface, the slower the loop, so most work moves down this list as it gets closer to done.

| Surface | Good for | Blind to |
| --- | --- | --- |
| `__web_preview` in a browser | Layout, spacing, colors, copy, component composition | Touch gestures, native a11y, native animation timing, safe areas |
| Lynx Go over QR | Gesture feel, scroll physics, real fonts and safe areas, native rendering | Anything needing a native module or `Info.plist` configuration |
| [Custom host in Xcode](/guides/testing-with-xcode) | Native modules, permissions, custom fonts, release behavior | Nothing, at the cost of a native build |

Vy UI's own component previews run the web path, which is why the docs describe native behavior in prose alongside them rather than expecting the preview to demonstrate it.

## When the QR code does not work

**The phone cannot reach the URL.** The address in the QR code is whichever LAN interface rspeedy picked, so a phone on guest Wi-Fi or a different VLAN will fail. Opening the Lynx URL in the phone's browser is the quickest way to confirm reachability before blaming the bundle.

**The port moved.** rspeedy increments past an occupied port, so a second project running concurrently shifts the second one to 3001 and the QR code you scanned five minutes ago now points at the wrong server.

**The app opens with visible chrome.** The active schema is the plain one rather than the fullscreen one, so press `a`.

**Nothing rebuilds on save.** Files outside the configured entry graph are not watched, which most often bites when editing a file that nothing imports yet.
