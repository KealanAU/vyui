[Lynx Go](/guides/testing-on-device) stops being enough the moment your app needs something the runtime does not ship. Camera capture, biometrics, keychain storage, push notifications, custom fonts, permission strings, and every third-party SDK live in native code that has to be compiled into an application, and Lynx Go contains only what its authors compiled into theirs.

The answer is a host app of your own, which turns out to be smaller than it sounds. A working iOS host is one Xcode target, four Swift files, and a Podfile. Once it exists, your normal `pnpm dev` loop continues to work, because the host loads the same bundle over the same LAN that the QR code points at.

Everything below is taken from a host that runs a Vue Lynx app with Vy UI components and a custom camera module on a physical iPhone, verified against Lynx 3.9.0 and Xcode 26.

## What you need once

Install the tooling and enable device installs before starting.

- Full Xcode, signed in with any Apple ID. A free personal team is enough for installing on your own device.
- `brew install cocoapods xcodegen`
- Developer Mode on the iPhone, under Settings → Privacy & Security.
- The phone and the Mac on the same network, since the host loads the bundle over HTTP from your dev server.

## Generating the project

Checking an `.xcodeproj` into git is a reliable way to generate merge conflicts nobody can read, so the project here is generated from a declarative spec by XcodeGen. The spec, the Podfile, and the Swift sources are the files you commit, and everything else is disposable.

Create `native/ios-host/project.yml`:

```yaml [project.yml]
name: VyHost
options:
  bundleIdPrefix: com.example
  deploymentTarget:
    iOS: '15.0'
  createIntermediateGroups: true
schemes:
  VyHost:
    build:
      targets:
        VyHost: all
    run:
      config: Debug
targets:
  VyHost:
    type: application
    platform: iOS
    sources:
      - path: HostSources
      - path: Assets.xcassets
    info:
      path: Info.plist
      properties:
        UILaunchScreen:
          UIColorName: LaunchBackground
        UISupportedInterfaceOrientations: [UIInterfaceOrientationPortrait]
        # UIKit warns and eventually asserts without a scene manifest.
        UIApplicationSceneManifest:
          UIApplicationSupportsMultipleScenes: false
          UISceneConfigurations:
            UIWindowSceneSessionRoleApplication:
              - UISceneConfigurationName: Default
                UISceneDelegateClassName: $(PRODUCT_MODULE_NAME).SceneDelegate
        NSLocalNetworkUsageDescription: Dev builds load the app from your Mac over the local network.
        NSAppTransportSecurity:
          # Dev only. The Release build phase below strips this from the product.
          NSAllowsArbitraryLoads: true
    settings:
      base:
        SWIFT_VERSION: '5.9'
        IPHONEOS_DEPLOYMENT_TARGET: '15.0'
        CODE_SIGN_STYLE: Automatic
```

## Pinning the pods

Lynx and PrimJS version independently, which is the first thing that trips up a manual Podfile. Lynx 3.9.0 pairs with PrimJS 3.8.0-alpha.6, and CocoaPods refuses to resolve a prerelease version unless you pin it explicitly. Check the "Integrate with Existing Apps" guide on lynxjs.org for the current compatible set before copying these numbers.

```ruby [Podfile]
source 'https://cdn.cocoapods.org/'

platform :ios, '15.0'

# Swift code doing `import Lynx` needs the pods built as importable modules.
use_modular_headers!

target 'VyHost' do
  pod 'Lynx', '3.9.0', :subspecs => ['Framework']
  pod 'PrimJS', '3.8.0-alpha.6', :subspecs => ['quickjs', 'napi']

  # Host services: image loading, logging, HTTP.
  pod 'LynxService', '3.9.0', :subspecs => ['Image', 'Log', 'Http']
  pod 'SDWebImage', '5.15.5'
  pod 'SDWebImageWebPCoder', '0.11.0'

  # Extended built-in elements (<x-input> and friends) that Vy UI renders.
  pod 'XElement', '3.9.0'
end

post_install do |installer|
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      config.build_settings['GCC_TREAT_WARNINGS_AS_ERRORS'] = 'NO'
      config.build_settings['SWIFT_TREAT_WARNINGS_AS_ERRORS'] = 'NO'
      config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '15.0'
    end
    # The Lynx podspec attaches -Werror as a per-file compiler flag, which the
    # build-settings override above cannot reach. On recent Xcode this fails the
    # build on iOS-13-era deprecations inside Lynx itself.
    next unless target.respond_to?(:source_build_phase)
    target.source_build_phase.files.each do |file|
      flags = file.settings && file.settings['COMPILER_FLAGS']
      next unless flags && flags.include?('-Werror')
      file.settings['COMPILER_FLAGS'] = flags.gsub('-Werror', '-Wno-error')
    end
  end
end
```

`XElement` is easy to leave out and annoying to debug. Several Vy UI components render Lynx's extended elements, so without that pod they come up empty rather than throwing.

## The Swift side

The host needs four files, none of them long.

`AppDelegate.swift` boots the runtime. The `LynxService` pods register themselves once linked, so there is nothing else to wire.

```swift [HostSources/AppDelegate.swift]
import Lynx
import UIKit

@main
class AppDelegate: UIResponder, UIApplicationDelegate {
    func application(
        _ application: UIApplication,
        didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?
    ) -> Bool {
        LynxEnv.sharedInstance()
        return true
    }
}
```

`SceneDelegate.swift` owns the window, and it also fixes a safe-area bug that costs an afternoon if you hit it cold. Lynx resolves `env(safe-area-inset-*)` from statics that `initLayoutConfig` populates by reading the key window, and that window is still nil while the `LynxView` is being constructed in `viewDidLoad`. The insets come back as zero, your layout sits under the notch, and nothing logs an error. Re-running it once the scene is active fixes it.

```swift [HostSources/SceneDelegate.swift]
import Lynx
import UIKit

class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?

    func scene(
        _ scene: UIScene,
        willConnectTo session: UISceneSession,
        options connectionOptions: UIScene.ConnectionOptions
    ) {
        guard let windowScene = scene as? UIWindowScene else { return }
        let window = UIWindow(windowScene: windowScene)
        window.rootViewController = ViewController()
        window.makeKeyAndVisible()
        self.window = window
    }

    func sceneDidBecomeActive(_ scene: UIScene) {
        // safe-area insets read as 0/0 when initLayoutConfig runs before the
        // window is key. Re-running it here is a harmless refresh.
        guard let window else { return }
        LynxEnv.sharedInstance().initLayoutConfig(window.bounds.size)
    }
}
```

`TemplateProvider.swift` fetches the bundle. The cache policy is the part that matters, because the dev server rewrites the bundle on every save and `URLSession` will happily serve you the previous one.

```swift [HostSources/TemplateProvider.swift]
import Foundation
import Lynx

final class TemplateProvider: NSObject, LynxTemplateProvider {
    func loadTemplate(withUrl urlString: String!, onComplete callback: LynxTemplateLoadBlock!) {
        guard let urlString, let url = URL(string: urlString) else {
            callback?(nil, NSError(
                domain: "VyHost",
                code: 1,
                userInfo: [NSLocalizedDescriptionKey: "Bad bundle URL: \(urlString ?? "nil")"]
            ))
            return
        }

        var request = URLRequest(url: url)
        request.cachePolicy = .reloadIgnoringLocalCacheData

        URLSession.shared.dataTask(with: request) { data, _, error in
            callback?(data, error)
        }.resume()
    }
}
```

`ViewController.swift` builds the `LynxView` and loads the bundle into it.

```swift [HostSources/ViewController.swift]
import Lynx
import UIKit

class ViewController: UIViewController {
    private var lynxView: LynxView?

    override func viewDidLoad() {
        super.viewDidLoad()

        let lynxView = LynxView { builder in
            let config = LynxConfig(provider: TemplateProvider())
            // Register custom native modules here:
            // config.register(MyNativeModule.self)
            builder.config = config
            builder.screenSize = self.view.frame.size
            builder.fontScale = 1.0
        }
        lynxView.preferredLayoutWidth = view.frame.size.width
        lynxView.preferredLayoutHeight = view.frame.size.height
        lynxView.layoutWidthMode = .exact
        lynxView.layoutHeightMode = .exact
        view.addSubview(lynxView)
        self.lynxView = lynxView

        lynxView.loadTemplate(fromURL: bundleURL, initData: nil)
    }
}
```

## Making the dev loop bearable

Hardcoding `http://192.168.1.x:3000/main.lynx.bundle` works exactly until you join a different network, and then it produces a blank screen with no explanation. Two small pieces remove that failure mode entirely.

A build phase writes the Mac's current LAN IP into the app bundle. Add it under the target in `project.yml`:

```yaml [project.yml]
    postBuildScripts:
      - name: Write dev server host
        basedOnDependencyAnalysis: false
        script: |
          set -u
          if [ "${CONFIGURATION}" = "Release" ]; then
            echo "Release build — skipping DevServerHost.txt."
            exit 0
          fi
          ip=$(ipconfig getifaddr en0 2>/dev/null || ipconfig getifaddr en1 2>/dev/null || echo localhost)
          DEST_DIR="${TARGET_BUILD_DIR}/${UNLOCALIZED_RESOURCES_FOLDER_PATH}"
          mkdir -p "${DEST_DIR}"
          printf '%s\n' "${ip}" > "${DEST_DIR}/DevServerHost.txt"
          echo "Dev server host: ${ip}"
```

Writing to `TARGET_BUILD_DIR` rather than the source tree keeps the generated file out of the repository.

The app then scans the rspeedy port range on that host and loads whichever server answers first, so the port shuffling that happens when you have two projects open stops mattering:

```swift [HostSources/ViewController.swift]
#if DEBUG
private let devServerPorts = Array(3000...3010)

private let devServerHost: String = {
    guard let url = Bundle.main.url(forResource: "DevServerHost", withExtension: "txt"),
          let contents = try? String(contentsOf: url, encoding: .utf8)
    else { return "localhost" }
    let host = contents.trimmingCharacters(in: .whitespacesAndNewlines)
    return host.isEmpty ? "localhost" : host
}()

/// Probes each candidate port with a cheap HEAD request; first 2xx wins.
private func discoverDevServer(completion: @escaping (String?) -> Void) {
    func tryPort(at index: Int) {
        guard index < devServerPorts.count else { return completion(nil) }
        let candidate = "http://\(devServerHost):\(devServerPorts[index])/main.lynx.bundle"
        guard let url = URL(string: candidate) else { return tryPort(at: index + 1) }
        var request = URLRequest(url: url, cachePolicy: .reloadIgnoringLocalCacheData, timeoutInterval: 1.0)
        request.httpMethod = "HEAD"
        URLSession.shared.dataTask(with: request) { _, response, _ in
            if let http = response as? HTTPURLResponse, (200...299).contains(http.statusCode) {
                completion(candidate)
            } else {
                tryPort(at: index + 1)
            }
        }.resume()
    }
    tryPort(at: 0)
}
#endif
```

Adopting `LynxViewLifecycle` and rendering `didRecieveError` into an on-screen label is worth the twenty lines it costs, because the default failure mode is a blank screen and the useful message is buried in the Xcode console.

## Running it

```sh
cd native/ios-host
xcodegen generate     # writes VyHost.xcodeproj from project.yml
pod install           # writes VyHost.xcworkspace
open VyHost.xcworkspace
```

Open the workspace rather than the project, or the pods will not be linked. Re-run both commands after editing `project.yml` or the `Podfile`.

In Xcode, select your iPhone as the destination, set your team under Signing & Capabilities, and run. Start `pnpm dev` in your app directory first so there is a server to find.

From then on the loop is the ordinary one. Editing a component and saving reloads the bundle on the device, and you only return to Xcode when the native side changes.

## Registering native modules

A custom native module is a Swift or Objective-C class registered on the `LynxConfig` that the `LynxView` builds with:

```swift
let config = LynxConfig(provider: TemplateProvider())
config.register(MyCameraModule.self)
config.register(MyStorageModule.self)
builder.config = config
```

Building a per-view config, as above, means the global registration helpers that some packages ship will not reach it, so register explicitly on the config you construct. Compiling the module's sources directly is usually simpler than wiring a podspec, and XcodeGen will pull them straight from an installed package:

```yaml [project.yml]
    sources:
      - path: HostSources
      - path: ../../node_modules/@some/native-package/ios
        name: NativePackage
        excludes:
          - 'README.md'
```

That path needs a `name` when `createIntermediateGroups` is on. Without it XcodeGen nests the group under the `../..` tree it derives for `node_modules` and doubles the path, and the build then cannot find any of the files.

## Custom fonts

A font referenced with `url(...)` from your CSS gets rewritten to `webpack:///static/font/…`, which native Lynx cannot fetch. Registering the font in the host and referring to it as `local("Family Name")` is the fix that keeps the bundle small:

```yaml [project.yml]
    sources:
      - path: ../ios/Resources/Fonts/YourFont-Regular.ttf
        group: Fonts
        buildPhase: resources
    info:
      properties:
        UIAppFonts:
          - YourFont-Regular.ttf
```

The name in your CSS has to match the font's internal family, full, or PostScript name rather than the filename. Inlining the font as a data URI is the alternative, and it is the only option if you also want the app to run in Lynx Go.

## Shipping a Release build

A Release build cannot reach your dev server, so the bundle has to travel inside the app. One build phase produces it and copies it in:

```yaml [project.yml]
      - name: Embed Lynx bundle
        basedOnDependencyAnalysis: false
        script: |
          set -u
          if [ "${CONFIGURATION}" != "Release" ]; then
            echo "Debug build — loading from the dev server instead."
            exit 0
          fi
          APP_DIR="${SRCROOT}/../.."
          # Xcode script phases get a minimal PATH; node is often managed by fnm.
          export PATH="/opt/homebrew/bin:/usr/local/bin:${HOME}/.local/share/fnm/aliases/default/bin:${PATH}"
          PNPM="$(command -v pnpm || true)"
          if [ -z "${PNPM}" ]; then
            echo "error: pnpm not found on PATH. Run \`pnpm build\` manually, then rebuild."
            exit 1
          fi
          (cd "${APP_DIR}" && "${PNPM}" build) || exit 1
          DEST_DIR="${TARGET_BUILD_DIR}/${UNLOCALIZED_RESOURCES_FOLDER_PATH}"
          mkdir -p "${DEST_DIR}"
          cp "${APP_DIR}/dist/main.lynx.bundle" "${DEST_DIR}/main.lynx.bundle"
```

Running `pnpm build` from a script phase needs `ENABLE_USER_SCRIPT_SANDBOXING: 'NO'` in the target's base settings, since the sandbox otherwise blocks writes outside the build directory.

A second phase removes the development-only Info.plist keys, so the shipped app carries no ATS exemption and never prompts for local network access:

```yaml [project.yml]
      - name: Strip dev Info.plist keys
        basedOnDependencyAnalysis: false
        script: |
          set -u
          [ "${CONFIGURATION}" = "Release" ] || exit 0
          PLIST="${TARGET_BUILD_DIR}/${INFOPLIST_PATH}"
          /usr/libexec/PlistBuddy -c "Delete :NSAppTransportSecurity" "${PLIST}" 2>/dev/null || true
          /usr/libexec/PlistBuddy -c "Delete :NSLocalNetworkUsageDescription" "${PLIST}" 2>/dev/null || true
```

Loading the embedded bundle is then a `#if DEBUG` branch away from the dev-server path:

```swift [HostSources/ViewController.swift]
private func loadEmbeddedBundle() {
    guard let url = Bundle.main.url(forResource: "main.lynx", withExtension: "bundle") else { return }
    guard let data = try? Data(contentsOf: url) else { return }
    lynxView?.loadTemplate(data, withURL: url.absoluteString)
}
```

::callout{icon="i-lucide-shield-check"}
Gating the ATS exemption behind Release stripping is worth doing from the start. App Review asks about `NSAllowsArbitraryLoads`, and a build phase that removes it is easier to explain than a justification for keeping it.
::

## When it does not work

**A blank screen** means the bundle fetch failed. Open the bundle URL in Safari on the phone; if the page does not load there, the problem is the network or the dev server rather than the host.

**An engine version mismatch on load** means the Lynx pod version and the bundle your rspeedy version produces disagree. Align the pod version with whatever the lynxjs.org integration guide pairs with your `@lynx-js/rspeedy`.

**Pod resolution failing** usually means the pinned set has drifted. Take the current versions from the same guide, and remember that PrimJS does not track Lynx's numbering.

**`-Werror` errors inside the Lynx pods** mean the `post_install` hook did not run or did not complete. Check the tail of `pod install` for an error.

**Layout sitting under the notch** is the safe-area initialisation described above, so confirm `initLayoutConfig` runs from `sceneDidBecomeActive`.

**Components rendering empty** where you expect an input or a text field usually means the `XElement` pod is missing.
