Lynx ships five native elements and leaves everything above them to you. `<view>`, `<text>`, `<image>`, `<scroll-view>`, and `<list>` cover layout and primitive rendering, so a real application still needs the entire tier that web developers take for granted, meaning dialogs that trap focus, sheets that respond to a drag, selects that manage a listbox, and sliders that track a gesture without dropping frames.

Two libraries fill that tier today. They bind to different frameworks and neither is a drop-in replacement for the other, so the choice usually follows from a decision you have already made about React or Vue.

::callout{icon="i-lucide-info"}
Vy UI is the Vue library described below, and we maintain it. The comparison names what the alternatives do better, because a page that pretended otherwise would not be much use to anyone choosing between them.
::

## The libraries

| Library | Framework | Layer | Components | License |
| --- | --- | --- | --- | --- |
| [`@lynx-js/lynx-ui`](https://github.com/lynx-family/lynx-ui) | ReactLynx | Headless | ~21 packages | Apache 2.0 |
| [`@vyui/core`](/packages/core) | Vue Lynx | Headless | 47 primitives | MIT |
| [`@vyui/kit`](/packages/kit) | Vue Lynx | Styled | 48 components | MIT |
| Lynx built-in elements | Any | Native | 5 elements | Apache 2.0 |

### lynx-ui, the official ReactLynx library

`@lynx-js/lynx-ui` is maintained by the Lynx team as the reference component library for ReactLynx. It is headless, so it hands you behavior and leaves the styling entirely open, and it is distributed as one npm package per component rather than a single barrel. The published set covers Button, Checkbox, Dialog, Draggable, FeedList, Form, Input, LazyComponent, List, Overlay, Popover, Presence, RadioGroup, ScrollView, Sheet, Slider, Sortable, SwipeAction, Swiper, and Switch, plus a shared `common` package underneath them.

Because it comes from the same team that builds the runtime, its behavior tends to track Lynx SDK changes closely, and it requires LynxSDK 3.2 or newer. If you are writing ReactLynx, this is the library to start with, and the per-component packaging means you only pay for the components you import.

What it does not do is style anything, and it does not support Vue. There is no ReactLynx equivalent to shadcn/ui or Vant sitting on top of it yet, so the visual layer of a ReactLynx app is still work you do yourself.

### Vy UI, for Vue Lynx

[Vue Lynx](/guides/vue-lynx) is a Vue 3 custom renderer for Lynx, and it cannot consume React components, so lynx-ui does not help there. Vy UI exists to fill that gap in two layers.

`@vyui/core` is the headless layer, with 47 primitives covering overlays and dialogs, menus and popovers, form controls, navigation, and the gesture-heavy surfaces that are hardest to get right on a dual-thread runtime: Swiper, SwipeAction, Sortable, Draggable, FeedList, and ScrollView all share a main-thread gesture core so drags do not round-trip through the background thread.

`@vyui/kit` is the styled layer, 48 components built on those primitives and themed through Tailwind Variants. A [three-tier semantic token system](/theming) means dark mode flips the whole component set through a single class rather than per-component `dark:` variants. There is also a [shadcn-style CLI](/getting-started/cli) that copies component source into your own repository when you would rather own the code than depend on the package.

Vy UI is alpha, and Vue Lynx itself is earlier than that, so the honest framing is that this is the library you use if you have already decided on Vue and accept that APIs will move. It is MIT licensed and community-maintained rather than official.

### Writing against the built-in elements

Skipping the libraries entirely is a real option for a small application, and it is worth naming because the component tier is where most of the difficulty in a Lynx app lives. Lynx gives you real CSS in external stylesheets, which covers more visual ground than React Native's style objects do, and `<list>` is already a virtualized recycler.

The cost shows up in behavior rather than appearance. A dialog needs its own focus and dismissal handling, a bottom sheet needs velocity-aware drag physics that run on the main thread, and a select needs keyboard and screen-reader wiring that Lynx does not infer. Those are the parts that take weeks and then break on one platform, which is the argument for a library.

## Choosing between them

The framework decision makes the library decision for you, so it is worth taking in that order.

Pick **ReactLynx and lynx-ui** if your team writes React, you want the option that moves in lockstep with the runtime, and you are comfortable building the styling layer. This is the better-supported path today and it is what most of the Lynx ecosystem assumes.

Pick **Vue Lynx and Vy UI** if your team writes Vue and rewriting into React is not the trade you want to make. You get a styled layer that ReactLynx does not have an equivalent for, and you accept a younger runtime underneath it. The [Vue Lynx guide](/guides/vue-lynx) covers what that runtime does and does not support.

Neither choice locks you into a rendering model that differs from the other, because both compile down to the same native Lynx elements on iOS, Android, and web.

## Where the ecosystem is thin

Three gaps apply across every option on this page, so they are worth checking before you commit to any of them.

Accessibility on web is incomplete in a way it is not on native. Lynx emits `accessibility-*` properties that iOS VoiceOver and Android TalkBack consume directly, but browsers ignore them, so a screen reader on the web target sees generic boxes unless a library mirrors them into ARIA. Vy UI documents this as [an open gap](/accessibility) rather than a solved problem.

Keyboard input on web is similarly unhandled. Lynx was designed for touch, and the browser target inherits that, so Escape-to-dismiss and arrow-key navigation in menus are not wired by default in either library.

Internationalization is early. `Intl` is not fully available in the Lynx runtime, so date and number formatting depend on polyfills, and RTL layout coverage is partial.

None of these are reasons to avoid Lynx. They are reasons to check the specific components you need against the specific targets you ship to, rather than assuming web parity with native.
