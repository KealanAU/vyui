Starting a Lynx project in 2026 means reaching for Tailwind v4, because that is what `npm create` gives you and what every current tutorial assumes. It does not work, and the failure is not the kind that explains itself: the build either errors on the preset or produces a stylesheet missing most of what you wrote.

Lynx needs Tailwind v3. As of 25 July 2026 the latest `@lynx-js/tailwind-preset` on npm is 0.5.0, and it still declares `peerDependencies: { tailwindcss: "^3.4.0" }`, unchanged from 0.4.0. The interesting part is why, because it is not a matter of somebody finding time to port it.

## What the Lynx preset actually does

Lynx renders through its own CSS engine rather than a browser, and that engine implements a subset of CSS. Utilities outside that subset are worse than useless, since a class that emits `float: left` or `--tw-ring-shadow` produces CSS the engine cannot act on, and you get a silent no-op instead of an error.

The preset's job is to stop those utilities existing in the first place. It does that with an allowlist:

```js
// inside @lynx-js/tailwind-preset
corePlugins: DEFAULT_CORE_PLUGINS  // an array, not an object
```

Passing an array to `corePlugins` in Tailwind v3 means *enable only these*. `DEFAULT_CORE_PLUGINS` holds 57 entries, against the 179 core plugins Tailwind v3 ships, so roughly two thirds of Tailwind is switched off before your config is even read. What survives is flexbox, sizing, spacing, colors, typography, borders, opacity, and z-index. What does not includes floats, most positioning, and the entire `ring` family, which is why a focus ring on Lynx has to be built from a spread-only `box-shadow` rather than `ring-2`.

Everything else the preset does sits on ordinary plugin APIs. It calls `matchUtilities` and `addUtilities` around 28 times each, `matchVariant` five times, and `addBase` twice, adding Lynx-specific utilities and the `ui-*` variants that replace the `data-[state]` selectors Lynx cannot match on.

## Why v4 cannot do this yet

Tailwind v4 removed `corePlugins`. Not renamed, not relocated. Searching the published `tailwindcss@4.3.0` package for the string finds nothing, because v4 has no mechanism for disabling parts of the utility set at all. Every utility is always available.

That is the blocker, and it is narrow but structural. The plugin APIs the preset leans on, `matchUtilities` and `addUtilities` and `matchVariant` and `addBase`, all still exist in v4 and would mostly port. Configuration moved from a JavaScript `presets` array to CSS-first `@theme` blocks, which is disruptive but tractable. The allowlist has no successor, so the preset's central job cannot be expressed in v4 as it stands.

Upstream cannot fix this alone either. Either Tailwind reintroduces some way to restrict the emitted utility set, or the Lynx preset takes a different approach entirely, such as post-processing the generated CSS to strip what the engine will not understand. Both are real work rather than a version bump, which is why [the tracking issue](https://github.com/KealanAU/vyui/issues/5) has stayed open since May.

## Running both versions in one repo

A monorepo that ships Lynx packages alongside a normal web docs site does not have to pick. Vy UI runs both, because the constraint is per-target rather than per-repository:

| Package | Tailwind | Why |
| --- | --- | --- |
| `@vyui/kit` | `^3.4.0` | Compiles for the Lynx CSS engine |
| Example apps | `^3.4.17` | Lynx apps |
| Docs site | `^4.0.0` | A browser app, so no preset and no constraint |

Anything rendering through Lynx takes v3. Anything rendering in a browser can take v4, and probably should. pnpm and other content-addressed installers handle the duplication without complaint, since the two versions never meet in a single module graph.

The rule worth writing down is that the Tailwind version follows the rendering engine, not the repository.

## What to do today

Pin v3 explicitly in any package that builds for Lynx, and use the v3 PostCSS pipeline rather than v4's:

```json [package.json]
{
  "devDependencies": {
    "tailwindcss": "^3.4.17",
    "@lynx-js/tailwind-preset": "^0.5.0",
    "rsbuild-plugin-tailwindcss": "^0.2.4"
  }
}
```

Reaching for `@tailwindcss/postcss`, `@tailwindcss/vite`, or `@tailwindcss/cli` is the most common way to end up here by accident, because those are v4-only packages and pull v4 in behind you.

Two v3 behaviours are worth knowing while you are pinned to it. Spacing has no half-steps above `3.5`, so `size-4.5` and `p-6.5` compile to nothing at all rather than failing, and the fix is an arbitrary value like `size-[18px]`. Classes built dynamically, such as `` `bg-${color}-500` ``, cannot be statically extracted and need a safelist, which matters more on Lynx than on the web because a missing class is invisible rather than merely unstyled.

Vy UI's [installation guide](/getting-started/installation) covers the preset wiring itself, including the `uiVariants` registration that the `ui-*` state classes depend on.
